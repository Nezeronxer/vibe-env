# Спецификация: Nightshift

Рабочее имя (ASSUMPTION R21). Переименование - замена строки.

## Задача

Я хочу поручать работу над кодом агентам и не сидеть рядом. Сейчас агент в терминале
останавливается на каждом разрешении, ждёт, пока я проверю результат, и молчит, когда
упёрся. Если запустить несколько, они мешают друг другу в одной папке, а я не знаю, кто
закончил, кто сломал, кто ждёт меня. Проверять каждый шаг - это и есть та работа,
которую я хотел отдать.

## Решение

Приложение для macOS и Linux. Я выбираю папку проекта, пишу задачу одной фразой и
ухожу. Агент работает в отдельной копии репозитория, сам прогоняет тесты, второй агент
проверяет его работу, и готовое вливается одним коммитом в main. Меня зовут
(системным уведомлением и списком «Нужен ты» в окне приложения) в трёх случаях: агенту нужно решение, которое
может принять только я; задача не вышла после всех попыток; нужно разрешение отправить
код наружу (push / PR). Ответить можно прямо из Telegram. Значок в строке меню всегда
показывает, сколько задач идёт и сколько ждут меня. Любую готовую задачу можно откатить
одной кнопкой.

## Словарь

- **Задача** - то, что поставил человек: текст + проект. Одна задача - одна ветка - один
  итоговый коммит.
- **Проект** - папка с git-репозиторием, добавленная в приложение.
- **Исполнитель** - агент, который делает задачу. **Ревьюер** - отдельный агент, который
  её проверяет, в свежем контексте.
- **Проверка** - команда тестов проекта (`npm test`, `cargo test`, …).
- **Финиш** - что происходит с готовой задачей: влить локально / влить и запушить / PR.
- **Наружу** - любое действие, которое видно вне машины: push, PR.

## Глубина по измерениям

| Измерение | Решение |
|---|---|
| **Первый запуск** | Нет проектов → пустой экран: «Перетащи сюда папку проекта», кнопка «Выбрать папку». Проверка движков: `claude` найден? Нет → карточка «Установи Claude Code: …» вместо поля задачи. Нет `git` → то же. |
| **Пусто** | Проект без задач → поле задачи + подсказка «Опиши, что сделать, одной фразой. Агент сам спросит, если что-то непонятно». Пустые группы скрыты. |
| **Неверный ввод** | Пустая задача - кнопка неактивна. Папка без git - предложение init. Неверный токен бота - причина в настройках, токен не теряется. Текст в поле задачи сохраняется при закрытии окна. |
| **Сбой** | Агент упал / ненулевой код → попытка засчитывается, повтор той же сессией; после 3 → «Не вышло» + последний вывод. Нет сети у агента → то же. Диск/git ошибка → «Не вышло» с текстом команды git и её stderr, worktree сохраняется. |
| **Обрыв** | Выход из приложения / перезагрузка: состояние на диске после каждого шага. При запуске задачи в «В работе» продолжаются: исполнитель - `resume` с «Продолжи с того места», проверка/ревью/вливание - запускаются заново (они идемпотентны). Двойной клик «Ответить» - второй ответ игнорируется (задача уже не ждёт). |
| **Рост** | Готовые старше 7 дней - в «Архив» (свёрнут). Worktree удаляется после финиша (в режиме PR - после открытия PR; ветка остаётся). «Не вышло» - worktree хранится до «Удалить»/«Повторить». Логи - файл на задачу, в карточке последние 500 событий. |
| **Права** | Исполнитель: только своя рабочая копия, без push/remote/sudo. Ревьюер: только чтение. Telegram: только привязанный чат. «Наружу» - по политике проекта. Приложение никогда не делает `--force`, `reset --hard` по веткам пользователя, не удаляет его ветки. |
| **Последствия** | Готово → один коммит в main, уведомление с итогом, кнопка «Откатить». Push/PR - по политике. Отменённая задача: worktree и ветка удаляются, main не тронута. |

## Решения по реализации

1. **Tauri 2 + Rust, интерфейс - обычные HTML/CSS/JS без фреймворка и без сборщика.** Одно приложение на обе ОС, лёгкое, системные уведомления/трей/горячие клавиши - готовые плагины Tauri. Интерфейс из 3 экранов не окупает React и Vite.
2. **Ядро - отдельная Rust-библиотека `core` без зависимости от Tauri.** Весь цикл задачи тестируется без окна: фейковый агент (скрипт, печатающий stream-json) + временный git-репозиторий.
3. **Агент - внешний CLI-процесс**, вывод читается построчно (stream-json / json-события) и переводится в общие события. Сессия агента продолжается через `--resume <id>` (Claude) / `--session <id>` (opencode) - так ответ человека и исправления после тестов/ревью идут в тот же контекст исполнителя.
4. **Вопрос человеку - строка `NEEDS_HUMAN:` в конце ответа исполнителя**, а не MCP-сервер. Работает с любым движком, ноль кода на протоколы. Правило - в системной добавке к промпту (`--append-system-prompt` у Claude; в тексте промпта у opencode).
5. **Права исполнителя.** У каждого адаптера - свой «автономный» флаг движка (Codex `--full-auto`/sandbox workspace-write, Gemini `--yolo` и т.п. - точные флаги по документации движка). Claude: `--permission-mode bypassPermissions` + `--settings` с запретами `Bash(git push:*)`, `Bash(git remote:*)`, `Bash(sudo:*)` и, если поддерживается установленной версией, песочницей Claude Code (запись только в рабочую копию). Без песочницы - в настройках приложения предупреждение «агенты работают без песочницы». Исполнитель таска проверяет точные ключи настроек по документации Claude Code. Грабля из опыта: deny-правила `Read(...)` превращаются в запрет ОС в песочнице - не запрещать `*.pem`, иначе ломается TLS у всех подпроцессов. Для «своей команды» запретов нет - в её настройке предупреждение.
6. **Ревьюер** - тот же движок, новая сессия, `--permission-mode plan` (только чтение), ответ - строго JSON `{"verdict":"approve"|"changes","issues":["…"]}`. Невалидный JSON → один повтор, затем считается «changes» с пометкой «ревьюер ответил не по формату».
7. **Коммиты делает приложение, не агент:** после хода исполнителя `git add -A && git commit` в его копии (если есть изменения). Финиш - squash: один коммит на main через `git commit-tree` от дерева перебазированной ветки. Так история чистая и откат = `git revert <sha>`.
8. **Продвижение main без порчи рабочей копии человека:** если основная копия стоит на main и чистая → `git merge --ff-only`; если на main и грязная → ждать (история 22); если на другой ветке → `git update-ref refs/heads/main <new> <old>` (атомарно, только вперёд).
9. **Вливание - одна очередь на проект** (мьютекс): перебазирование → проверка → (если ветка изменилась от rebase) короткое ревью не повторяется, только тесты → продвижение main.
10. **Хранилище - JSON-файлы** в каталоге данных приложения (`~/Library/Application Support/nightshift` / `~/.local/share/nightshift`): `state.json` (проекты, настройки, задачи) с записью через временный файл + rename, `logs/<task>.jsonl`. Объёмы - сотни задач, база не нужна.
11. **Токен Telegram - в системной связке ключей** (`keyring`: Keychain / Secret Service); если связка недоступна (Linux без Secret Service) - файл с правами 0600 и предупреждение. В `state.json` и логах токена нет.
12. **Telegram - long polling `getUpdates`** из Rust (`reqwest`, прокси из настроек или `HTTPS_PROXY`). Сервер и вебхуки не нужны.
13. **GitHub - через системные `git` и `gh`**: авторизация та, что уже настроена у человека. Своих OAuth и токенов GitHub приложение не хранит.
14. **Лимит подписки** распознаётся адаптером по тексту результата (`usage limit`, `limit reached`, `resets …`); время сброса - из текста, иначе +30 мин.

Машина состояний задачи (`Task.status`):

```
queued → preparing → working ⇄ checking → reviewing → merging → done
                        │  ↑        │            │          │
                        ↓  │        └─(fail ≤3)──┘          ├→ awaiting_outward → done
                 needs_human        (changes ≤2) → working  ├→ merge_blocked (грязная main) → merging
                 paused_limit → working                     └→ done_not_pushed (push не вышел)
любой → failed (попытки кончились / конфликт / ошибка git) · любой → cancelled · done → reverted
```

Дополнено таском 03 (D01): у проекта с `finish=Push` и `ask_outward` откат идёт `done → reverted → awaiting_outward (push_revert) → reverted` - revert-коммит уходит в origin только после «да» человека. Задача, закоммиченная агентом с файлом из `copy_files` (например `.env`), чистится до вливания; не вычистилось - `failed: hidden_file_committed`. У PR-задачи отката нет: `pr_no_undo`.

**Швы для тестов:** один главный - `Engine` с адаптером `fake` (скрипт печатает заданные события и правит файлы) поверх временного git-репозитория. Через него проверяются истории 2, 4-9, 17-22, 24, 28, 30, 34. Второй - `Adapter::parse` на сохранённых строках настоящего вывода Claude/opencode. Третий - `git` на временных репозиториях (продвижение main в трёх случаях). UI и Telegram - ручная проверка.
