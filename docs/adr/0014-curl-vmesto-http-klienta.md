# 0014. Сеть ядра идёт через системный `curl`

## Контекст

В v4 ядру впервые нужен HTTP GET: каталоги скиллов, MCP и модов, реестр npm, models.dev. До этого сеть шла только через `git` и `gh`, которые ядро запускает как процессы.

## Решение

Модуль `core::net` вызывает системный `curl` через `Command`, так же как `git` и `gh`. На каждый вызов задаются лимит размера и тайм-аут. Разрешён только https. Вызов спрятан за `trait Fetch`, в тестах стоит `FakeFetch`. Если `curl` не найден, возвращается ключ `curl_missing`, и интерфейс объясняет причину.

## Почему

- Крейт-HTTP-клиент отвергнут: он тянет в приложение новую зависимость и свой TLS-стек. Одно это расширяет и поверхность атаки, и список для аудита зависимостей. Приложение, которое скачивает недоверенное, должно быть тут скромнее.
- Единообразие: `git`, `gh` и `curl` запускаются одним способом, ошибки и тайм-ауты разбираются в одном месте.
- Трейт нужен, чтобы тесты каталога и обновлений не ходили в сеть: `FakeFetch` отвечает заранее заданным.

## Последствия

- Теперь у приложения есть жёсткая зависимость от наличия `curl` в системе. Отсутствие - отдельная ошибка, а не падение.
- Каждый запрос - отдельный процесс, переиспользования соединений нет. Официальный реестр MCP на живом прогоне отвечал ~21 с, SkillsMP и Smithery не ответили за 20 с и выключены по умолчанию.
- Ответ режется по лимиту размера (`--max-filesize`), всё сверх него приходит как ошибка `TooLarge`.
- Все `curl`-вызовы нужно проверять на то, что URL не может стать флагом. Иначе `--yolo` из недоверенного ответа превратится в аргумент (так было с идентификатором модели, F4.1).
